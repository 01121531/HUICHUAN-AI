# 代理管理与自动切换设计方案

> 文档状态：设计稿，尚未实施
>
> 适用项目：HUICHUAN-AI
>
> 核心约定：通用日志中耗时指标显示为红色时，本方案将其视为一次代理超时。

## 1. 建设目标

在现有渠道请求链路中增加代理管理能力，支持：

- HTTP、HTTPS、SOCKS4、SOCKS5 代理。
- 将代理划分到不同分组，并按渠道绑定代理分组。
- 按请求次数或连续使用时间自动更换代理。
- 定时检测代理是否可连接，以及出口 IP 是否符合预期。
- 从通用日志读取真实业务请求耗时，并使用与前端红色状态完全一致的规则判断超时。
- 代理连续多次超时后自动暂停，并切换到同组其他可用代理。
- 暂停一段时间后自动解除标记并进行恢复测试。
- 恢复测试仍连续超时时，再次暂停并延长冷却时间。
- 代理切换期间阻塞该分组的新请求，避免请求继续使用失效代理。
- 在系统设置中提供中文代理管理页面、运行状态和操作记录。

## 2. 设计原则

1. **以真实业务日志为准**：代理慢请求判断使用通用日志，不使用独立测速结果代替真实业务表现。
2. **连接检测和耗时判断分离**：定时检测只判断代理能否建立连接；日志分析负责判断代理是否过慢。
3. **请求必须关联具体代理**：每条相关通用日志都要记录实际使用的 `proxy_id`，不能只根据渠道推测代理。
4. **只影响对应分组**：一个代理组切换时，不阻塞其他代理组或未启用代理的渠道。
5. **并发切换只能执行一次**：同一代理组在同一时间只能存在一个切换操作。
6. **已有请求不强行中断**：切换时阻塞新请求，已经发送给上游的请求继续执行。
7. **所有阈值可配置**：文档中的数值均为建议默认值，可在分组级别覆盖。

## 3. 总体结构

```text
渠道
  ↓ 绑定
代理分组
  ↓ 选择当前代理
具体代理 IP
  ↓
发送上游请求
  ↓
通用日志记录 proxy_id
  ↓
日志分析器复用前端红色规则
  ↓
更新连续超时次数和窗口统计
  ↓
暂停代理 / 切换代理 / 冷却恢复
```

## 4. 通用日志超时计算

### 4.1 数据来源

只分析满足以下条件的通用日志：

- 日志类型为消费日志或错误日志，即当前前端会展示耗时指标的日志类型。
- 日志已经记录有效的 `proxy_id`。
- 日志对应真实发送到上游的请求。

建议使用的日志字段：

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `proxy_id` | 实际处理请求的代理 ID | - |
| `proxy_group_id` | 请求发生时所属代理组 | - |
| `request_id` | 请求唯一标识 | - |
| `is_stream` | 是否为流式请求 | - |
| `use_time` | 请求总耗时 | 秒 |
| `completion_tokens` | 输出 Token 数量 | Token |
| `other.frt` | 首字响应耗时 | 毫秒 |

### 4.2 首字响应时间

流式请求按首字响应时间判断：

| 首字响应时间 | 前端颜色 | 代理判断 |
| --- | --- | --- |
| `< 5 秒` | 绿色 | 正常 |
| `5 秒至不足 10 秒` | 黄色 | 偏慢但不超时 |
| `>= 10 秒` | 红色 | 超时 |

计算方式：

```text
首字响应时间 = 第一次收到上游响应的时间 - 请求开始时间
```

后端日志中的 `frt` 使用毫秒，因此判断公式为：

```text
首字超时 = is_stream 为 true 且 frt >= 10000
```

非流式请求不计算首字超时。

### 4.3 小输出请求的总耗时

当 `completion_tokens < 100` 时，按总耗时判断：

| 总耗时 | 前端颜色 | 代理判断 |
| --- | --- | --- |
| `< 10 秒` | 绿色 | 正常 |
| `10 秒至不足 30 秒` | 黄色 | 偏慢但不超时 |
| `>= 30 秒` | 红色 | 超时 |

公式：

```text
小输出总耗时超时 = completion_tokens < 100 且 use_time >= 30
```

### 4.4 大输出请求的生成速度

当 `completion_tokens >= 100` 且 `use_time > 0` 时，按 TPS 判断，避免长文本因为总时间较长而被误判。

```text
TPS = completion_tokens / use_time
```

| TPS | 前端颜色 | 代理判断 |
| --- | --- | --- |
| `>= 30` | 绿色 | 正常 |
| `>= 15 且 < 30` | 黄色 | 偏慢但不超时 |
| `< 15` | 红色 | 超时 |

公式：

```text
大输出速度超时 = completion_tokens >= 100
                 且 use_time > 0
                 且 completion_tokens / use_time < 15
```

### 4.5 最终红色判定

一次请求只要任意一个耗时指标为红色，就视为一次代理超时：

```text
代理超时 = 首字响应为红色
           或 小输出请求总耗时为红色
           或 大输出请求 TPS 为红色
```

等价伪代码：

```go
firstResponseTimeout := isStream && frtMilliseconds >= 10_000

durationTimeout := completionTokens < 100 && useTimeSeconds >= 30

throughputTimeout := completionTokens >= 100 &&
    useTimeSeconds > 0 &&
    float64(completionTokens)/float64(useTimeSeconds) < 15

timeout := firstResponseTimeout || durationTimeout || throughputTimeout
```

### 4.6 不计入代理超时的情况

以下情况不应仅因为请求失败就计入代理超时：

- API Key 无效。
- 余额不足或额度不足。
- 模型不存在。
- 请求参数错误。
- 内容审核拒绝。
- 上游快速返回的业务错误。
- 用户主动取消请求。
- 请求还没有发往上游就被系统拦截。

如果错误日志本身的耗时指标达到红色条件，则仍按红色超时处理。

## 5. 连续超时和窗口计算

仅依靠单次红色请求容易受到网络抖动影响，因此同时使用连续计数和滑动窗口。

### 5.1 连续超时

```text
红色请求：consecutive_timeouts + 1
正常请求：consecutive_timeouts = 0
黄色请求：建议清零，不按超时累计
```

默认连续超时阈值：

```text
consecutive_timeout_threshold = 3
```

当同一代理连续 3 次请求为红色时，立即暂停该代理并切换。

### 5.2 滑动窗口

默认读取代理最近 10 个可判断耗时的请求：

```text
窗口超时率 = 窗口内红色请求数 / 窗口有效请求数
```

默认参数：

```text
window_size = 10
window_timeout_ratio = 60%
minimum_samples = 3
```

触发条件：

```text
窗口有效请求数达到 10 且红色请求数达到 6
```

### 5.3 最终暂停条件

```text
连续红色次数 >= 3
或者
最近 10 次请求中红色次数 >= 6
```

连续规则用于快速发现持续故障，窗口规则用于发现间歇性慢代理。

## 6. 代理状态机

### 6.1 状态定义

| 状态 | 含义 | 是否接收正常请求 |
| --- | --- | --- |
| `normal` | 代理正常 | 是 |
| `watching` | 已出现少量红色请求，继续观察 | 是 |
| `switching` | 正在切换当前代理 | 否，新请求等待 |
| `cooldown` | 已自动暂停，等待冷却结束 | 否 |
| `probing` | 冷却结束，正在进行恢复测试 | 仅允许测试流量 |
| `unavailable` | 定时连接检测失败 | 否 |
| `disabled` | 管理员手动禁用 | 否 |

### 6.2 状态流转

```text
normal
  ↓ 出现 1 至 2 次连续红色
watching
  ↓ 达到暂停条件
cooldown
  ↓ 当前代理正在服务流量时触发切换
switching
  ↓ 切换完成
cooldown
  ↓ 冷却时间结束
probing
  ↓ 连续恢复测试正常
normal
  ↓ 恢复测试仍连续红色
cooldown
```

管理员手动禁用时直接进入 `disabled`，不会被定时恢复任务自动启用。

## 7. 冷却和恢复测试

### 7.1 冷却时间

首次自动暂停默认冷却 10 分钟。恢复失败后采用指数退避：

```text
冷却时间 = min(10 分钟 × 2 ^ 连续恢复失败次数, 2 小时)
```

示例：

| 恢复失败次数 | 冷却时间 |
| --- | --- |
| 0 | 10 分钟 |
| 1 | 20 分钟 |
| 2 | 40 分钟 |
| 3 | 80 分钟 |
| 4 及以上 | 120 分钟 |

代理恢复正常并稳定运行一段时间后，将连续恢复失败次数清零。

### 7.2 恢复测试

冷却结束后不能直接恢复全部流量，先进入 `probing`：

1. 执行一次基础连接检测。
2. 连接检测成功后，允许少量真实测试请求通过该代理。
3. 测试请求仍写入通用日志，并按相同红色规则判断。
4. 默认连续 2 次测试请求均非红色，恢复为 `normal`。
5. 任意测试请求为红色，重新进入 `cooldown` 并增加退避级别。

如果暂时没有真实业务请求，可保持 `probing` 状态等待测试流量，不应仅凭连接检测就判定完全恢复。

## 8. 定时有效性检测

### 8.1 检测内容

默认每 5 分钟对可检测代理执行：

- 域名解析是否成功。
- TCP 连接是否成功。
- HTTPS 场景下 TLS 握手是否成功。
- HTTP 请求是否获得有效响应。
- 检测请求耗时。
- 当前出口 IP。

### 8.2 检测结果使用方式

- 连续 2 次连接检测失败：标记为 `unavailable`。
- 连接检测恢复：进入 `probing`，不直接恢复全部流量。
- 检测耗时只作为管理页面参考，不替代通用日志红色判定。
- 管理员可以为代理配置预期出口 IP，发现出口 IP 变化时记录告警。

## 9. 请求次数和使用时间切换

代理组支持以下三个自动切换条件，任意一个满足即可触发：

1. **请求次数**：例如当前代理成功接收 500 个上游请求后切换。
2. **使用时间**：例如当前代理连续使用 30 分钟后切换。
3. **异常状态**：达到日志超时条件或连接检测失败后立即切换。

请求计数只包含已经选择代理并准备发送到上游的请求，不包含：

- 参数校验失败。
- 身份验证失败。
- 等待队列中取消的请求。
- 代理切换超时后未发出的请求。

切换成功后，当前轮次的请求计数和开始时间重新计算；累计历史统计不清零。

## 10. 代理选择算法

候选代理首先排除：

- `disabled`。
- `cooldown`。
- `unavailable`。
- 尚未完成恢复测试的代理。
- 超出管理员配置使用范围的代理。

候选代理排序建议：

1. 优先选择当前轮次未使用或最久未使用的代理。
2. 优先选择最近窗口超时率较低的代理。
3. 优先选择最近平均首字响应时间较低的代理。
4. 指标相同时按轮询顺序选择。

不建议始终选择历史最快代理，否则流量会长期集中在同一个出口 IP。首期可使用轮询加健康状态过滤，后续再增加权重选择。

当分组内没有可用代理时：

- 如果分组允许直连回退，则使用直连并明确记录 `proxy_id = 0` 和回退原因。
- 如果不允许直连回退，则等待指定时间后返回服务暂不可用。
- 默认建议关闭直连回退，避免业务流量意外暴露服务器出口 IP。

## 11. 切换期间阻塞请求

### 11.1 切换流程

```text
1. 获取代理组级切换锁
2. 将代理组设置为 switching
3. 新请求进入该组的等待队列
4. 已经发送的请求继续执行
5. 选择并初始化新的代理连接配置
6. 原子替换当前代理
7. 重置本轮请求次数和开始时间
8. 将代理组恢复为可用状态
9. 唤醒等待队列
10. 释放切换锁
```

### 11.2 阻塞边界

- 只阻塞正在切换的代理组。
- 不阻塞其他代理组。
- 不阻塞未绑定代理组的渠道。
- 等待操作必须响应客户端取消信号。
- 默认最大等待时间为 30 秒。
- 默认每个代理组最多等待 500 个请求。

超过等待时间或队列上限时，返回明确的服务暂不可用错误，不允许无限堆积请求。

### 11.3 并发控制

同一代理组使用单独的互斥锁或单航班机制：

- 第一个请求负责触发切换。
- 其他并发请求只等待结果，不重复执行切换。
- 当前代理必须通过原子引用或受锁保护的状态读取。
- 切换失败时必须解除等待，不能让队列永久阻塞。

## 12. 数据库设计建议

### 12.1 代理分组表 `proxy_groups`

主要字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 分组 ID |
| `name` | 分组名称 |
| `enabled` | 是否启用 |
| `current_proxy_id` | 当前代理 |
| `status` | 分组状态 |
| `max_requests` | 单代理最大请求数 |
| `max_duration_seconds` | 单代理最大使用时间 |
| `switch_wait_seconds` | 切换最大等待时间 |
| `max_waiting_requests` | 最大等待请求数 |
| `health_check_interval` | 连接检测周期 |
| `consecutive_timeout_threshold` | 连续红色阈值 |
| `window_size` | 滑动窗口大小 |
| `window_timeout_ratio` | 窗口红色比例阈值 |
| `base_cooldown_seconds` | 基础冷却时间 |
| `max_cooldown_seconds` | 最大冷却时间 |
| `recovery_success_count` | 恢复所需正常次数 |
| `allow_direct_fallback` | 无可用代理时是否允许直连 |

### 12.2 代理表 `proxies`

主要字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 代理 ID |
| `group_id` | 所属代理组 |
| `name` | 代理名称 |
| `protocol` | HTTP、HTTPS、SOCKS4、SOCKS5 |
| `host`、`port` | 代理地址 |
| `username`、`password` | 认证信息，密码需加密或受保护存储 |
| `enabled` | 管理员是否启用 |
| `status` | 当前状态 |
| `last_exit_ip` | 最近检测到的出口 IP |
| `last_check_at` | 最近检测时间 |
| `last_check_latency_ms` | 最近检测耗时 |
| `health_failures` | 连续连接检测失败次数 |
| `consecutive_timeouts` | 连续红色次数 |
| `recovery_failures` | 连续恢复失败次数 |
| `cooldown_until` | 冷却结束时间 |
| `last_used_at` | 最近使用时间 |
| `total_requests` | 累计请求数 |
| `total_timeouts` | 累计红色请求数 |

代理 URL、用户名和密码不得输出到普通日志。

### 12.3 渠道绑定表 `channel_proxy_bindings`

主要字段：

| 字段 | 说明 |
| --- | --- |
| `channel_id` | 渠道 ID，唯一索引 |
| `proxy_group_id` | 绑定的代理组 |
| `enabled` | 是否启用代理 |

### 12.4 通用日志扩展

建议在日志实体增加：

| 字段 | 说明 |
| --- | --- |
| `proxy_id` | 实际处理请求的代理，必须建立索引 |
| `proxy_group_id` | 请求发生时所属代理组，可选索引 |

可在 `other.admin_info` 中附加脱敏后的代理名称和分组名称，方便管理页面显示，但不能只把 `proxy_id` 存在 JSON 中。原因是：

- JSON 查询在 SQLite、MySQL、PostgreSQL 和 ClickHouse 中实现不同。
- JSON 字段难以建立统一、高效的索引。
- 日志量增大后，按代理统计会产生明显性能问题。

数据库迁移需要同时覆盖当前项目支持的日志存储方式，尤其是 ClickHouse 日志表结构。

### 12.5 分析进度和去重

日志分析任务不能重复累计同一请求。建议维护独立分析记录或进度表，唯一键至少包含：

```text
proxy_id + request_id + log_type
```

不建议只依赖日志自增 ID，因为不同数据库或 ClickHouse 日志表的 ID 行为可能不同。

## 13. 后台任务

建议拆分为三个职责明确的后台任务：

### 13.1 通用日志分析任务

- 周期性读取尚未分析且 `proxy_id > 0` 的日志。
- 计算首字颜色、总耗时颜色和 TPS 颜色。
- 更新连续红色次数、滑动窗口和累计统计。
- 达到条件时触发代理暂停和切换。
- 通过唯一键保证同一日志只分析一次。

### 13.2 代理连接检测任务

- 按分组配置的周期检测代理连接。
- 更新出口 IP、检测耗时和连接失败次数。
- 连续失败时触发不可用状态和切换。

### 13.3 冷却恢复任务

- 查找 `cooldown_until` 已到期的代理。
- 先执行连接检测，再进入 `probing`。
- 根据真实测试请求的通用日志决定恢复或再次冷却。

## 14. 系统设置页面

在“系统设置”中增加“代理管理”菜单，全部使用中文。

### 14.1 页面组成

- **代理分组**：创建分组、配置切换和超时策略。
- **代理列表**：维护协议、地址、认证和状态。
- **渠道绑定**：将渠道绑定到代理组。
- **运行状态**：查看当前代理、等待队列和切换状态。
- **异常记录**：查看暂停、恢复、检测失败和切换历史。

### 14.2 代理列表建议字段

| 字段 | 展示方式 |
| --- | --- |
| 代理名称 | 文本 |
| 协议 | 标签 |
| 地址 | 脱敏显示 |
| 所属分组 | 分组名称 |
| 当前状态 | 中文状态标签 |
| 当前轮次请求数 | 数值 |
| 当前轮次使用时间 | 时长 |
| 最近首字时间 | 毫秒或秒 |
| 最近 TPS | 数值 |
| 最近窗口红色率 | 百分比 |
| 连续红色次数 | 数值 |
| 冷却剩余时间 | 倒计时 |
| 最近检测时间 | 时间 |
| 出口 IP | 脱敏或完整显示，由权限决定 |

### 14.3 管理操作

- 启用或禁用代理。
- 立即检测。
- 立即切换代理。
- 手动解除暂停并进入恢复测试。
- 清空当前观察计数。
- 查看该代理对应的通用日志。
- 查看切换和状态变更记录。

## 16. 异常和边界处理

- 分组只有一个代理时，代理暂停后不能原地继续使用，应进入等待或返回服务暂不可用。
- 所有代理都在冷却时，取最早可恢复时间用于页面提示。
- 服务重启后从数据库恢复代理状态、当前代理和冷却时间。
- 多实例部署时，切换锁和当前代理状态需要使用共享存储或数据库锁，不能只使用进程内锁。
- 通用日志延迟写入时，分析任务按日志实际到达顺序处理，并使用请求时间辅助排序。
- 同一请求产生多条日志时，通过 `request_id` 去重，避免一次请求累计多次超时。
- 请求重试后使用了不同代理时，每次真实上游尝试应记录对应代理，最终日志结构要能区分尝试次数。
- 修改代理账号密码后，需要使旧连接池失效，避免继续使用旧认证信息。

## 18. 验收标准

1. 每条经过代理的消费或错误日志能够准确查到实际 `proxy_id`。
2. 后端计算出的红色结果与通用日志页面颜色完全一致。
3. 首字时间达到 10 秒时被判定为超时。
4. 小于 100 个输出 Token 且总耗时达到 30 秒时被判定为超时。
5. 不少于 100 个输出 Token 且 TPS 低于 15 时被判定为超时。
6. 连续 3 次红色后，代理自动暂停并切换到同组可用代理。
7. 切换期间新请求进入等待队列，不会继续使用旧代理。
8. 切换完成后等待请求能够正常继续执行。
9. 等待超过 30 秒或队列超过限制时能够及时返回错误。
10. 冷却结束后代理只接收恢复测试流量，测试通过后才恢复正常。
11. 恢复测试再次失败时，代理重新暂停且冷却时间增加。
12. 定时连接检测失败不会错误修改通用日志的红色判断结果。
13. 服务重启后代理状态、冷却时间和渠道绑定不会丢失。
14. 管理页面不展示代理密码，不在普通日志中输出完整代理连接地址。

## 19. 当前方案结论

本方案以现有通用日志的红色显示规则作为唯一的业务耗时超时标准，同时用独立连接检测判断代理是否能够连接。两类结果分别负责“慢”和“断”，最终共同驱动代理暂停、切换和恢复。

实施前最重要的前置条件是让每个真实上游请求及其通用日志准确关联 `proxy_id`。如果缺少该字段，在同一渠道轮换多个代理后无法判断究竟是哪个代理产生红色请求，自动暂停结果将不可靠。
