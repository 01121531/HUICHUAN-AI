# 代理管理与自动切换设计方案

> 文档状态：部分实施（当前开发分支已完成数据与日志关联、红色日志自动判定、分组级切换阻塞、多实例数据库切换租约、冷却恢复、定时健康检测和主要管理操作；逐次上游尝试日志及 SOCKS4 仍待完成）
>
> 适用项目：HUICHUAN-AI
>
> 最近更新：2026-08-04
>
> 核心约定：通用日志中耗时指标显示为红色时，本方案将其视为一次代理超时。

## 0. 当前实施基线

### 0.1 v1.1.3 已完成

本次先遵循“不改变渠道其他行为，只让原代理地址可变”的约束，在现有渠道 `Proxy` 字段上实现轻量轮换，没有新增数据库表。

| 能力 | 当前实现 |
| --- | --- |
| 多代理录入 | 渠道代理地址支持每行一个或使用英文逗号分隔，并自动去空、去重 |
| 请求选取 | 每次真实上游请求都按渠道读取当前代理，单代理保持原有行为 |
| 次数轮换 | 同一代理默认使用 500 次请求后切换到下一个 |
| 时间轮换 | 同一代理默认连续使用 1800 秒后切换到下一个 |
| 网络失败切换 | 创建代理客户端或发送上游请求失败时，当前代理冷却 60 秒，下次请求选择其他代理 |
| 并发保护 | 单个渠道的代理选取和状态修改使用互斥锁，避免并发请求重复修改轮换状态 |
| 日志关联 | 消费日志和错误日志的 `admin_info` 记录本次使用的 `proxy_index` |
| 配置界面 | 渠道管理中的代理地址改为多行输入框，并提供中文填写提示 |
| 兼容性 | 继续复用原渠道代理客户端，当前支持 HTTP、HTTPS、SOCKS5、SOCKS5H |

当前默认值位于 `service/channel_proxy_rotator.go`：

```text
ChannelProxyRotateRequests = 500
ChannelProxyRotateSeconds = 1800
ChannelProxyFailCooldownSeconds = 60
```

以上轮换状态保存在当前服务进程内。服务重启或渠道代理列表变化时，状态会重新开始计算。

## 1. 建设目标

在现有渠道请求链路中增加代理管理能力，支持：

- HTTP、HTTPS、SOCKS4、SOCKS5 代理。
- 将代理划分到不同分组，并按渠道绑定代理分组。
- 按请求次数或连续使用时间自动更换代理。
- 定时检测代理是否可连接，以及出口 IP 是否符合预期。
- 从通用日志读取真实业务请求耗时，并使用与前端红色状态完全一致的规则判断超时。
- 代理连续多次超时后自动暂停，并切换到同组其他可用代理。
- 暂停一段时间后自动解除标记并进行恢复测试。
- 恢复测试仍连续超时时，再次暂停并延长冷却时间。
- 代理切换期间阻塞该分组的新请求，避免请求继续使用失效代理。
- 在系统设置中提供中文代理管理页面、运行状态和操作记录。

## 2. 设计原则

1. **以真实业务日志为准**：代理慢请求判断使用通用日志，不使用独立测速结果代替真实业务表现。
2. **连接检测和耗时判断分离**：定时检测只判断代理能否建立连接；日志分析负责判断代理是否过慢。
3. **请求必须关联具体代理**：每条相关通用日志都要记录实际使用的 `proxy_id`，不能只根据渠道推测代理。
4. **只影响对应分组**：一个代理组切换时，不阻塞其他代理组或未启用代理的渠道。
5. **并发切换只能执行一次**：同一代理组在同一时间只能存在一个切换操作。
6. **已有请求不强行中断**：切换时阻塞新请求，已经发送给上游的请求继续执行。
7. **所有阈值可配置**：文档中的数值均为建议默认值，可在分组级别覆盖。

```text

```

## 4. 通用日志超时计算

### 4.1 数据来源

只分析满足以下条件的通用日志：

- 日志类型为消费日志或错误日志，即当前前端会展示耗时指标的日志类型。
- 日志已经记录有效的 `proxy_id`。
- 日志对应真实发送到上游的请求。

建议使用的日志字段：

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `proxy_id` | 实际处理请求的代理 ID | - |
| `proxy_group_id` | 请求发生时所属代理组 | - |
| `request_id` | 请求唯一标识 | - |
| `is_stream` | 是否为流式请求 | - |
| `use_time` | 请求总耗时 | 秒 |
| `completion_tokens` | 输出 Token 数量 | Token |
| `other.frt` | 首字响应耗时 | 毫秒 |

### 4.2 首字响应时间

流式请求按首字响应时间判断：

| 首字响应时间 | 前端颜色 | 代理判断 |
| --- | --- | --- |
| `< 5 秒` | 绿色 | 正常 |
| `5 秒至不足 10 秒` | 黄色 | 偏慢但不超时 |
| `>= 10 秒` | 红色 | 超时 |

计算方式：

```text
首字响应时间 = 第一次收到上游响应的时间 - 请求开始时间
```

后端日志中的 `frt` 使用毫秒，因此判断公式为：

```text
首字超时 = is_stream 为 true 且 frt >= 10000
```

非流式请求不计算首字超时。

### 4.3 小输出请求的总耗时

当 `completion_tokens < 100` 时，按总耗时判断：

| 总耗时 | 前端颜色 | 代理判断 |
| --- | --- | --- |
| `< 10 秒` | 绿色 | 正常 |
| `10 秒至不足 30 秒` | 黄色 | 偏慢但不超时 |
| `>= 30 秒` | 红色 | 超时 |

公式：

```text
小输出总耗时超时 = completion_tokens < 100 且 use_time >= 30
```

### 4.4 大输出请求的生成速度

当 `completion_tokens >= 100` 且 `use_time > 0` 时，按 TPS 判断，避免长文本因为总时间较长而被误判。

```text
TPS = completion_tokens / use_time
```

| TPS | 前端颜色 | 代理判断 |
| --- | --- | --- |
| `>= 30` | 绿色 | 正常 |
| `>= 15 且 < 30` | 黄色 | 偏慢但不超时 |
| `< 15` | 红色 | 超时 |

公式：

```text
大输出速度超时 = completion_tokens >= 100
                 且 use_time > 0
                 且 completion_tokens / use_time < 15
```

### 4.5 最终红色判定

一次请求只要任意一个耗时指标为红色，就视为一次代理超时：

```text
代理超时 = 首字响应为红色
           或 小输出请求总耗时为红色
           或 大输出请求 TPS 为红色
```

等价伪代码：

```go
firstResponseTimeout := isStream && frtMilliseconds >= 10_000

durationTimeout := completionTokens < 100 && useTimeSeconds >= 30

throughputTimeout := completionTokens >= 100 &&
    useTimeSeconds > 0 &&
    float64(completionTokens)/float64(useTimeSeconds) < 15

timeout := firstResponseTimeout || durationTimeout || throughputTimeout
```

### 4.6 不计入代理超时的情况

以下情况不应仅因为请求失败就计入代理超时：

- API Key 无效。
- 余额不足或额度不足。
- 模型不存在。
- 请求参数错误。
- 内容审核拒绝。
- 上游快速返回的业务错误。
- 用户主动取消请求。
- 请求还没有发往上游就被系统拦截。

如果错误日志本身的耗时指标达到红色条件，则仍按红色超时处理。

## 5. 连续超时和窗口计算

仅依靠单次红色请求容易受到网络抖动影响，因此同时使用连续计数和滑动窗口。

### 5.1 连续超时

```text
红色请求：consecutive_timeouts + 1
正常请求：consecutive_timeouts = 0
黄色请求：建议清零，不按超时累计
```

默认连续超时阈值：

```text
consecutive_timeout_threshold = 3
```

当同一代理连续 3 次请求为红色时，立即暂停该代理并切换。

### 5.2 滑动窗口

默认读取代理最近 10 个可判断耗时的请求：

```text
窗口超时率 = 窗口内红色请求数 / 窗口有效请求数
```

默认参数：

```text
window_size = 10
window_timeout_ratio = 60%
minimum_samples = 3
```

触发条件：

```text
窗口有效请求数达到 10 且红色请求数达到 6
```

### 5.3 最终暂停条件

```text
连续红色次数 >= 3
或者
最近 10 次请求中红色次数 >= 6
```

连续规则用于快速发现持续故障，窗口规则用于发现间歇性慢代理。

## 6. 代理状态机

### 6.1 状态定义

| 状态 | 含义 | 是否接收正常请求 |
| --- | --- | --- |
| `normal` | 代理正常 | 是 |
| `watching` | 已出现少量红色请求，继续观察 | 是 |
| `switching` | 正在切换当前代理 | 否，新请求等待 |
| `cooldown` | 已自动暂停，等待冷却结束 | 否 |
| `probing` | 冷却结束，正在进行恢复测试 | 仅允许测试流量 |
| `unavailable` | 定时连接检测失败 | 否 |
| `disabled` | 管理员手动禁用 | 否 |

当前代码为兼容已有字段使用 `available`、`watching`、`switching`、`cooling`、`recovering`、`unavailable`、`paused` 和 `disabled`。其中 `available` 对应本文 `normal`，`cooling` 对应 `cooldown`，`recovering` 对应 `probing`，`paused` 表示管理员手动暂停。

### 6.2 状态流转

```text
normal
  ↓ 出现 1 至 2 次连续红色
watching
  ↓ 达到暂停条件
cooldown
  ↓ 当前代理正在服务流量时触发切换
switching
  ↓ 切换完成
cooldown
  ↓ 冷却时间结束
probing
  ↓ 连续恢复测试正常
normal
  ↓ 恢复测试仍连续红色
cooldown
```

管理员手动禁用时直接进入 `disabled`，不会被定时恢复任务自动启用。

## 7. 冷却和恢复测试

### 7.1 冷却时间

首次自动暂停默认冷却 10 分钟。恢复失败后采用指数退避：

```text
冷却时间 = min(10 分钟 × 2 ^ 连续恢复失败次数, 2 小时)
```

示例：

| 恢复失败次数 | 冷却时间 |
| --- | --- |
| 0 | 10 分钟 |
| 1 | 20 分钟 |
| 2 | 40 分钟 |
| 3 | 80 分钟 |
| 4 及以上 | 120 分钟 |

代理恢复正常并稳定运行一段时间后，将连续恢复失败次数清零。

### 7.2 恢复测试

冷却结束后不能直接恢复全部流量，先进入 `probing`：

1. 执行一次基础连接检测。
2. 连接检测成功后，允许少量真实测试请求通过该代理。
3. 测试请求仍写入通用日志，并按相同红色规则判断。
4. 默认连续 2 次测试请求均非红色，恢复为 `normal`。
5. 任意测试请求为红色，重新进入 `cooldown` 并增加退避级别。

如果暂时没有真实业务请求，可保持 `probing` 状态等待测试流量，不应仅凭连接检测就判定完全恢复。

当前开发分支已实现上述流程：冷却到期后先执行代理连接检测，成功后进入 `recovering`，再通过真实业务日志累计恢复结果；恢复失败会重新计算冷却截止时间并增加退避级别。

## 8. 定时有效性检测

### 8.1 检测内容

默认每 5 分钟对可检测代理执行：

- 域名解析是否成功。
- TCP 连接是否成功。
- HTTPS 场景下 TLS 握手是否成功。
- HTTP 请求是否获得有效响应。
- 检测请求耗时。
- 当前出口 IP。

### 8.2 检测结果使用方式

- 连续 2 次连接检测失败：标记为 `unavailable`。
- 连接检测恢复：进入 `probing`，不直接恢复全部流量。
- 检测耗时只作为管理页面参考，不替代通用日志红色判定。
- 管理员可以为代理配置预期出口 IP，发现出口 IP 变化时记录告警。

当前健康检测目标可通过 `PROXY_HEALTH_CHECK_URL` 配置，默认请求 `https://api64.ipify.org?format=json`；单次检测超时可通过 `PROXY_HEALTH_CHECK_TIMEOUT_SECONDS` 配置，默认 10 秒。检测异常只保存脱敏原因码，不保存包含代理凭据的原始错误文本。

## 9. 请求次数和使用时间切换

代理组支持以下三个自动切换条件，任意一个满足即可触发：

1. **请求次数**：例如当前代理成功接收 500 个上游请求后切换。
2. **使用时间**：例如当前代理连续使用 30 分钟后切换。
3. **异常状态**：达到日志超时条件或连接检测失败后立即切换。

请求计数只包含已经选择代理并准备发送到上游的请求，不包含：

- 参数校验失败。
- 身份验证失败。
- 等待队列中取消的请求。
- 代理切换超时后未发出的请求。

切换成功后，当前轮次的请求计数和开始时间重新计算；累计历史统计不清零。

## 10. 代理选择算法

候选代理首先排除：

- `disabled`。
- `cooldown`。
- `unavailable`。
- 尚未完成恢复测试的代理。
- 超出管理员配置使用范围的代理。

候选代理排序建议：

1. 优先选择当前轮次未使用或最久未使用的代理。
2. 优先选择最近窗口超时率较低的代理。
3. 优先选择最近平均首字响应时间较低的代理。
4. 指标相同时按轮询顺序选择。

不建议始终选择历史最快代理，否则流量会长期集中在同一个出口 IP。首期可使用轮询加健康状态过滤，后续再增加权重选择。

当分组内没有可用代理时：

- 如果分组允许直连回退，则使用直连并明确记录 `proxy_id = 0` 和回退原因。
- 如果不允许直连回退，则等待指定时间后返回服务暂不可用。
- 默认建议关闭直连回退，避免业务流量意外暴露服务器出口 IP。

## 11. 切换期间阻塞请求

### 11.1 切换流程

```text
1. 获取代理组级切换锁
2. 将代理组设置为 switching
3. 新请求进入该组的等待队列
4. 已经发送的请求继续执行
5. 选择并初始化新的代理连接配置
6. 原子替换当前代理
7. 重置本轮请求次数和开始时间
8. 将代理组恢复为可用状态
9. 唤醒等待队列
10. 释放切换锁
```

### 11.2 阻塞边界

- 只阻塞正在切换的代理组。
- 不阻塞其他代理组。
- 不阻塞未绑定代理组的渠道。
- 等待操作必须响应客户端取消信号。
- 默认最大等待时间为 30 秒。
- 默认每个代理组最多等待 500 个请求。

超过等待时间或队列上限时，返回明确的服务暂不可用错误，不允许无限堆积请求。

### 11.3 并发控制

同一代理组使用单独的互斥锁或单航班机制：

- 第一个请求负责触发切换。
- 其他并发请求只等待结果，不重复执行切换。
- 当前代理必须通过原子引用或受锁保护的状态读取。
- 切换失败时必须解除等待，不能让队列永久阻塞。

当前开发分支已完成单进程内的分组级门控、等待上限、超时退出和取消传播，并增加数据库共享切换租约。租约使用唯一所有者和截止时间原子抢占；只有当前所有者能提交或撤销切换，租约过期后旧所有者无法覆盖新结果。其他实例通过数据库 `switching` 状态等待，服务异常退出后由请求链路或健康任务回收过期租约。等待请求数量仍按实例分别限制，后续再增加跨实例全局汇总。

## 16. 异常和边界处理

- 分组只有一个代理时，代理暂停后不能原地继续使用，应进入等待或返回服务暂不可用。
- 所有代理都在冷却时，取最早可恢复时间用于页面提示。
- 服务重启后从数据库恢复代理状态、当前代理和冷却时间。
- 多实例部署时使用数据库切换租约保护当前代理更新；进程内门控只负责本实例已经进入选择阶段的请求，其他实例通过共享 `switching` 状态等待。
- 通用日志延迟写入时，分析任务按日志实际到达顺序处理，并使用请求时间辅助排序。
- 同一请求产生多条日志时，通过 `request_id` 去重，避免一次请求累计多次超时。
- 请求重试后使用了不同代理时，每次真实上游尝试应记录对应代理，最终日志结构要能区分尝试次数。
- 修改代理账号密码后，需要使旧连接池失效，避免继续使用旧认证信息。

## 18. 验收标准

当前开发分支已通过代理日志分析、切换门控、数据库租约单所有者、过期租约接管、旧所有者提交拒绝、跨实例状态等待、等待超时、队列上限、客户端取消、无可用代理等待、健康检测、预期出口 IP、冷却恢复、真实请求探测、再次退避和管理接口的定向自动化测试。前端格式检查、静态检查和生产构建已通过。以下条目仍作为最终联调验收清单，其中 SOCKS4 不属于当前已完成范围。

1. 每条经过代理的消费或错误日志能够准确查到实际 `proxy_id`。
2. 后端计算出的红色结果与通用日志页面颜色完全一致。
3. 首字时间达到 10 秒时被判定为超时。
4. 小于 100 个输出 Token 且总耗时达到 30 秒时被判定为超时。
5. 不少于 100 个输出 Token 且 TPS 低于 15 时被判定为超时。
6. 连续 3 次红色后，代理自动暂停并切换到同组可用代理。
7. 切换期间新请求进入等待队列，不会继续使用旧代理。
8. 切换完成后等待请求能够正常继续执行。
9. 等待超过 30 秒或队列超过限制时能够及时返回错误。
10. 冷却结束后代理只接收恢复测试流量，测试通过后才恢复正常。
11. 恢复测试再次失败时，代理重新暂停且冷却时间增加。
12. 定时连接检测失败不会错误修改通用日志的红色判断结果。
13. 服务重启后代理状态、冷却时间和渠道绑定不会丢失。
14. 管理页面不展示代理密码，不在普通日志中输出完整代理连接地址。

## 19. 当前方案结论

本方案以现有通用日志的红色显示规则作为唯一的业务耗时超时标准，同时用独立连接检测判断代理是否能够连接。两类结果分别负责“慢”和“断”，最终共同驱动代理暂停、切换和恢复。

v1.1.3 已完成渠道内轻量代理轮换。当前开发分支进一步完成稳定代理实体、代理分组、渠道绑定、兼容迁移、通用日志代理 ID、红色日志自动分析、分组级切换阻塞、多实例数据库切换租约、定时健康检测、冷却恢复、真实请求探测和中文管理页面。

下一阶段优先补充逐次上游尝试日志和 SOCKS4 支持；管理页面后续增加等待队列实时数量、跨实例全局队列上限、清空观察计数和按代理跳转通用日志。
