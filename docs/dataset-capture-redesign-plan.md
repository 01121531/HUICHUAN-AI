# 截获数据逻辑与管理页面重构方案

> 文档状态：已实施，作为验收与维护基线
>
> 最后更新：2026-07-15
> 适用范围：New API 内置采集、截获数据管理页面、权限、审计、筛选与 JSONL 导出

## 1. 目标

重构截获数据的运行策略、管理员授权、查询页面和导出流程：

- 系统设置只负责控制是否截获以及允许截获哪些站点模型。
- Root 在用户管理中为每个管理员单独授予查看和下载权限。
- 截获数据页面不再以 JSONL 文件为业务对象，而是按用户名组织截获记录。
- 支持按时间、模型、令牌、分组、渠道 ID 和内容筛选。
- 支持选择多个用户或多条记录，并合并导出为一个 JSONL 文件。
- 导出数据继续遵守既定的固定 11 个顶层字段 Schema。
- 查看、下载、删除和权限变更均进入管理审计记录，审计日志不包含截获正文。

## 2. 领域边界

### 2.1 核心对象

| 对象 | 含义 |
|---|---|
| 截获策略 | 是否开启截获、模型范围以及选中的站点模型 |
| 截获权限 | Root 为单个管理员授予的查看和下载能力 |
| 截获用户 | 产生截获记录的真实站点用户 |
| 截获记录 | 一次完整成功的模型调用快照 |
| 截获对话 | 同一用户、令牌和会话标识下的一组截获记录 |
| 查询索引 | 用于页面筛选和聚合的非正文元数据 |
| 导出任务 | 将选中的用户或记录合并为一个 JSONL 的过程 |

### 2.2 不变量

- 系统运行策略和人员访问权限必须相互独立。
- Root 始终拥有查看、下载、删除和配置权限。
- 普通用户始终不能访问截获数据管理接口。
- 管理员下载权限必须依赖查看权限。
- 删除继续保持 Root-only，不作为可分配的管理员权限。
- 页面和 API 不接受客户端提供的磁盘路径，只使用服务端生成的 opaque ID。
- 列表接口不返回完整提示词、工具参数或模型响应。
- JSONL 只作为存储和导出格式，不作为页面的信息架构。
- 未完整成功、取消、响应中断、归一化失败或 Schema 校验失败的调用不进入主数据集。
- 禁用截获或修改模型策略只影响新请求，不删除历史记录。

## 3. 管理员权限设计

删除系统设置中的全局 `DatasetCaptureAdminVisible` 开关，改为 Root 在“用户管理 -> 编辑管理员 -> 管理员权限”中逐人授权。

| 角色 | 查看列表和详情 | 下载 | 删除 | 配置策略 | 分配权限 |
|---|---:|---:|---:|---:|---:|
| Root | 是 | 是 | 是 | 是 | 是 |
| 仅有查看权限的管理员 | 是 | 否 | 否 | 否 | 否 |
| 有查看和下载权限的管理员 | 是 | 是 | 否 | 否 | 否 |
| 普通用户 | 否 | 否 | 否 | 否 | 否 |

新增权限资源 `dataset_capture`：

- `view`：显示侧边栏入口、访问用户分类、筛选、记录列表和记录详情。
- `download`：下载单条、单个用户或多用户合并数据；后端同时要求 `view`。
- 删除不进入权限目录，继续通过 Root API 鉴权。

用户编辑抽屉仅在目标用户为管理员且当前操作者为 Root 时显示该权限组。关闭 `view` 时前端自动关闭 `download`，后端仍独立验证权限，不能依赖页面隐藏。

### 3.1 旧配置迁移

- 旧 `DatasetCaptureAdminVisible=true` 时，一次性为现有管理员迁移 `view + download`，保持升级前行为。
- 旧值为 `false` 时不授予管理员截获权限。
- 新建管理员默认没有截获权限。
- 迁移完成后旧开关不再参与鉴权，并在后续版本移除。

## 4. 系统设置设计

系统设置只管理系统如何截获，不再管理谁能访问数据。

### 4.1 配置项

```text
DatasetCaptureEnabled: boolean
DatasetCaptureModelMode: "all" | "selected"
DatasetCaptureModels: string[]
```

`DatasetCaptureModels` 在数据库中保存为 JSON 数组，不使用逗号字符串。

### 4.2 页面结构

```text
截获数据
[开启截获数据                                      开关]

采集模型
[全部模型] [指定模型]

指定模型时：
[gpt-5.2 x] [claude-sonnet-4 x] [还有 11 项] [搜索输入]
[选择全部] [清空]
```

模型选择复用渠道表单现有的 Chip 多选样式，支持搜索、删除、自动换行和“还有 N 项”。模型候选来自站点当前可路由模型目录，禁止创建不存在的模型。

已经选中但后来下线的模型显示“已不可用”，不得静默删除。指定模型模式下不允许保存空列表。三个配置字段通过一个类型化策略接口原子保存，避免逐字段更新产生中间非法状态。

### 4.3 模型匹配语义

截获准入按客户端请求的站点模型判断，训练样本中的 `model` 继续保存最终映射后的上游模型。

```text
站点请求模型：gpt-5.2
渠道映射结果：gpt-5.2-2026-06-01
采集策略匹配：gpt-5.2
JSONL model：gpt-5.2-2026-06-01
```

页面的历史记录模型筛选针对已经保存的最终模型。系统设置中的截获模型范围和历史页面的模型筛选是两个不同概念。

## 5. 截获数据页面

### 5.1 页面业务层级

页面不再展示 JSONL 文件名、磁盘路径、`source_row` 或文件列表。页面统一使用以下业务层级：

```text
用户名
  └── 截获记录
       ├── 时间
       ├── 模型
       ├── 令牌
       ├── 实际使用分组
       ├── 最终渠道 ID
       ├── 对话 ID
       └── 请求和响应详情
```

### 5.2 页面布局

```text
截获数据  [运行中]                                      [刷新]

[时间范围] [模型] [令牌] [分组] [渠道 ID] [内容关键词]
[用户名搜索]                                  [重置筛选]

[ ] 张三  ID: 12   3 个令牌   46 条匹配记录   最近：10:32
  时间       模型       令牌      分组   渠道ID   对话    操作
  10:32:11   gpt-5.2    codex     vip    18       a81f... 查看
  10:21:06   gpt-5.2    codex     vip    21       a81f... 查看

[ ] 李四  ID: 19   2 个令牌   13 条匹配记录   最近：09:48
  [展开记录]

[已选择 2 个用户，共 59 条记录]                 [导出为一个 JSONL]
```

用户名是一级分类。每个用户组支持展开、折叠和勾选，折叠状态保存在浏览器本地。用户组内按截获时间倒序显示，并独立分页或按需加载，避免一次读取大用户的全部记录。

### 5.3 筛选条件

| 筛选项 | 数据来源 | 规则 |
|---|---|---|
| 时间 | `created_at` | 开始和结束时间，精确到秒 |
| 模型名称 | 最终样本 `model` | 可搜索、多选 |
| 令牌 | 真实令牌 ID 和名称 | 可搜索、多选 |
| 分组 | 请求最终实际使用的路由分组 | 可搜索、多选 |
| 渠道 ID | 最终成功 attempt 的渠道 | 可输入 ID，也可从现有渠道选择 |
| 内容 | system、messages、response 和 tool 内容 | 服务端关键词查询 |
| 用户名 | 真实用户名和用户 ID | 模糊搜索 |

同一筛选维度中的多个值使用 OR，不同筛选维度之间使用 AND。例如：

```text
最近 7 天
AND 模型为 gpt-5.2 或 claude-sonnet-4
AND 分组为 vip
AND 渠道 ID 为 18
```

内容关键词不进入审计日志，也不建立持久化明文全文索引。服务端先通过时间、用户、模型、令牌、分组和渠道缩小候选范围，再读取候选记录进行正文匹配。

### 5.4 详情面板

点击“查看”打开右侧详情面板：

- `概览`：用户名、用户 ID、令牌、分组、渠道 ID、请求模型、最终模型和时间。
- `消息`：按角色展示 system、user、assistant 和工具结果。
- `响应`：文本、停止原因和工具调用。
- `用量`：输入、输出和缓存 Token。
- `原始数据`：仅在高级标签中显示格式化 JSON。

列表默认不返回完整提示词或响应。只有打开详情时才读取正文并记录 `dataset_capture.view`。

## 6. 选择与合并导出

### 6.1 选择层级

- 勾选用户名：选择该用户名在当前筛选条件下的全部匹配记录，不局限于当前展开页。
- 勾选单条记录：只选择指定截获记录。
- 表头全选：选择当前完整筛选结果中的全部用户名。
- 用户级选择与单条选择发生重叠时，服务端自动去重。

页面底部使用固定批量操作栏，持续显示选中用户数、记录数和预计导出大小。筛选条件发生变化时清除旧选择，避免隐藏选择被误导出。

### 6.2 单文件导出规则

- 所有选中用户和记录合并为一个 `.jsonl` 文件。
- 每条截获快照占一行，不包裹为 JSON 数组。
- 排序为“用户 ID -> 令牌 ID -> 对话 ID -> 创建时间正序”，保证同一对话连续。
- 导出继续严格保持固定 11 个顶层字段，不增加用户名、令牌、分组或渠道 ID 字段。
- 页面显示真实用户名和令牌；导出中的 `user_id_hash` 继续遵守既定 Schema。
- 文件名使用 `dataset-capture-<时间>-<记录数>-records.jsonl`。

服务端先在权限为 `0600` 的临时文件中生成完整结果，并逐行验证 JSON 和固定 Schema。全部成功后再开始下载；磁盘不足、记录损坏或权限变化时不提供半个导出文件。临时文件在下载完成或失败后删除。

### 6.3 固定 JSONL 输出契约

导出文件每行是一条独立 JSON 记录，顶层字段集合和顺序固定为以下 11 项：

```text
session_id
user_id_hash
model
user_agent
system_prompt
tools
messages
response
created_at
cwd
_meta
```

约束如下：

- `messages` 统一为 Anthropic 风格的 `{role, content}`，系统消息移入 `system_prompt`。
- OpenAI function tools 统一为 `{name, description, input_schema}`。
- OpenAI、Anthropic 和 Gemini 的工具调用、工具结果统一为 `tool_use`、`tool_result` 内容块。
- 多模态内容完整保留，包括 URL、文件信息和内联 Base64。
- `response` 固定包含 `content`、`stop_reason`、`tool_use` 和 `usage`。
- `usage` 固定包含输入、输出与缓存 Token 结构；供应商缺失的计数使用 `0`。
- `_meta` 固定保存版本、来源、行号、最终用户输入、原始结束原因等既定元数据。
- 页面显示所需的真实用户名、令牌、分组和渠道信息只进入查询索引，不增加到导出 Schema。
- 导出前逐行执行严格字段集合校验；任意一行失败时整次导出失败，不返回部分文件。

## 7. 查询索引

新增可重建的 `dataset_capture_index` 元数据索引，不改变训练 JSONL：

```text
capture_id、node、file_id、row
user_id、token_id、user_group
requested_model、effective_model
channel_id、session_id、created_at、record_size
```

索引不保存认证 Header、Cookie、令牌密钥、提示词、响应正文或绝对磁盘路径。

新请求必须先成功写入并校验 JSONL，之后才能增加索引。删除记录时同步删除索引。服务启动时执行校正，清理不存在的索引项并补录可恢复的历史记录。

旧数据中无法恢复的分组、渠道 ID 或请求模型显示“未知”，仍可通过用户名、令牌、最终模型和时间浏览及导出。

## 8. API 设计

### 8.1 查询与详情

- `GET /api/dataset-captures/users`：按筛选条件分页返回用户分类、匹配数量、令牌数量和最近时间。
- `GET /api/dataset-captures/users/:user_id/records`：分页加载某个用户的匹配记录。
- `GET /api/dataset-captures/facets`：返回模型、令牌、分组和渠道筛选候选。
- `GET /api/dataset-captures/records/:capture_id`：读取完整详情并记录查看审计。

### 8.2 导出与删除

- `POST /api/dataset-captures/export`：按选中用户、选中记录和筛选快照生成一个 JSONL。
- `DELETE /api/dataset-captures/records/batch`：Root 批量删除记录或完整对话。

导出请求必须提交明确的选中用户 ID、记录 ID 和规范化筛选条件。服务端重新执行鉴权与范围解析，不接受文件路径或前端计算的记录数量。

## 9. 审计设计

| 事件 | 触发条件 | 非敏感元数据 |
|---|---|---|
| `dataset_capture.view` | 打开记录详情 | 操作人、capture ID、用户 ID、令牌 ID、结果 |
| `dataset_capture.download` | 合并导出成功 | 操作人、用户数、记录数、模型条件、时间范围、字节数 |
| `dataset_capture.delete` | Root 删除成功 | 操作人、记录或对话 ID、删除数量、结果 |
| `dataset_capture.permission_update` | Root 修改管理员权限 | 目标管理员 ID、变更前后权限 |
| `dataset_capture.policy_update` | Root 修改运行策略 | 开关、模型模式、模型数量和变更摘要 |

审计日志不得包含内容关键词、system prompt、messages、response、工具参数、认证信息或绝对文件路径。

## 10. 状态与失败处理

```text
请求进入
  -> 读取不可变策略快照
  -> 未开启或模型不匹配：不创建截获会话
  -> 匹配：暂存请求和最终成功 attempt
  -> 响应完整交付且归一化成功
  -> 校验固定 Schema
  -> 原子追加 JSONL
  -> 更新查询索引
```

- 失败 attempt、非 2xx、客户端取消、不完整 SSE 和 Schema 错误不写入主数据集。
- 索引更新失败不能破坏已经写入的 JSONL，由后台校正任务补录。
- 查询索引不可用时页面返回明确错误，不退化为无界目录扫描。
- 批量删除返回逐项结果；失败项保持选中，允许重试。
- 导出期间权限被撤销时立即终止并删除临时文件。

## 12. 验收标准

- Root 可以为单个管理员分别设置查看和下载权限。
- 未授权管理员无法通过菜单或直接 API 访问截获数据。
- 系统设置可以从站点现有模型中选择截获范围，指定模式不能保存空列表。
- 页面不显示 JSONL 文件、路径或行号，只显示用户名和业务记录。
- 用户分类支持展开、折叠、分页、单选、用户级选择和筛选结果全选。
- 时间、模型、令牌、分组、渠道 ID、用户名和内容筛选可以组合使用。
- 选择多个用户名后只下载一个合法 JSONL，记录不重复且同一对话连续。
- 导出文件逐行通过固定 11 字段 Schema 验证。
- 查看、下载、删除、权限修改和策略修改均产生不含正文的审计记录。
- 旧文件继续可浏览和导出；旧记录缺失的索引字段明确显示“未知”。
- 并发写入、筛选、导出和删除不会产生交叉 JSON、半条记录或路径越界。
- 桌面、平板和移动端页面均无文字遮挡、操作重叠或横向失控。

## 13. 分阶段实施与测试门禁

每一阶段必须在对应测试通过后再进入下一阶段；失败时只修复当前阶段，不通过回滚其他业务代码解决。

### 阶段 1：权限与迁移

- 建立 `dataset_capture.view`、`dataset_capture.download` 权限。
- 完成旧全局管理员可见配置的一次性迁移。
- 验证 Root、已授权管理员、未授权管理员和普通用户的 API 与菜单行为。

测试门禁：权限单元测试、路由中间件测试、用户权限编辑器目标 lint。

### 阶段 2：采集策略与模型范围

- 建立原子策略快照和专用策略 API。
- 从站点当前可用模型中选择“全部模型”或“指定模型”。
- 验证客户端请求模型用于准入、映射后模型用于样本输出。

测试门禁：策略单元测试、各协议模型提取测试、系统设置构建与交互测试。

### 阶段 3：元数据索引与查询

- 写入可重建的非正文索引。
- 提供用户聚合、记录分页、组合筛选、筛选候选和详情接口。
- 对历史 JSONL 执行索引校正，不覆盖已存在的有效元数据。

测试门禁：索引迁移、并发写入、历史重建、组合筛选、内容候选上限和路径 allow-list 测试。

### 阶段 4：合并导出与批量删除

- 支持用户级、记录级和当前筛选结果选择，并在服务端去重。
- 生成一个临时 JSONL，逐行校验固定 11 字段 Schema 后下载。
- Root 按完整对话文件执行批量删除，并同步清理索引。
